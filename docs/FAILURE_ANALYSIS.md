# 실패 원인과 재시도 — 2026-10-26

## 개발 환경과 소스 복구

관리 실행 환경이 executor 구성 기능을 조회하는 단계에서 시작하지 못했습니다. 로컬 명령은 실행할 수 없었습니다. 이 제어 계층의 상세 로그와 기존 디스크에 접근할 수 없어 근본 원인, 파일 삭제 또는 손상 여부는 확인하지 못했습니다. GitHub 연결 인증과는 별개의 장애입니다.

GitHub 앱을 통한 원격 파일 읽기와 브랜치 쓰기는 실제로 성공했습니다. 확인 가능한 원격 `2bfe225`를 기준으로 별도 브랜치에서 재구현하고 GitHub Actions에서 빌드·시험합니다. 이전 미푸시 0.8.0 ZIP·패치·커밋·APK의 복구를 주장하지 않습니다. 환경 비공개 식별자나 인증 정보는 저장소에 기록하지 않습니다.

## Release 게시 권한

첫 게시 시도는 빌드 산출물과 전체 Android 19건을 재확인한 뒤 Release 생성에서 HTTP 403 `Resource not accessible by integration`을 반환했습니다. 작업 토큰에는 Contents write가 표시됐습니다. 앱 코드가 같고 문서·CI만 추가된 현재 게시 커밋을 태그 대상으로 바꾸자 Release 생성과 7개 자산 업로드가 성공했습니다. 이는 이전 커밋의 새 태그 생성 경로에서 발생한 제한과 일치하며, 서버 내부 권한 판정 로그까지 확인한 것은 아닙니다. APK를 재빌드하거나 검증하지 않은 바이너리로 바꾸지 않습니다. 이전 Release나 태그를 덮어쓰지 않습니다.

업로드 후 재다운로드에서는 GitHub CLI의 바이너리 제어 문자 출력 보호가 Git bundle을 중단시켰습니다. 바이너리는 HTTP 스트림으로 파일에 직접 저장하고, 인증 헤더는 최초 GitHub API 요청에만 사용해 CDN 리디렉션에 전달하지 않습니다. 이미 만든 비공개 초안의 ID·작성자·대상·자산 목록을 확인하고, 모든 파일의 크기·SHA-256이 원래 검증 산출물과 같을 때만 게시합니다.

## 통과 판정

CI의 Android 단계는 실패 증거와 APK를 보존하기 위해 continue-on-error를 사용합니다. 따라서 워크플로의 초록색 표시만으로 Android 통과를 선언하지 않습니다. 실제 단계 outcome, JUnit failures/errors, ANDROID_TEST_SUMMARY 및 검증 ZIP의 summary.json을 함께 확인합니다. Release는 실제 Android 단계가 성공한 커밋의 동일 산출물만 재사용합니다. 전체 필수 19건과 실패·오류·생략 0을 재확인하며, 원래 SHA256SUMS·소스 ZIP의 Git blob·태그 커밋·업로드 후 내려받은 파일까지 대조합니다. 배포 문서/CI만 추가한 커밋 때문에 APK를 다시 만들지 않습니다.

실제 휴대폰, 실제 한국어 IME 조합, 모든 문서 형식의 고급 개체·서식 보존은 별도 인수 대상입니다. 실행하지 않은 검사는 통과 수에 포함하지 않습니다.
