# 전체 페이지·스크롤·확대 뷰어 개선 — 실제 진단과 검증 기록

작성: 2026-10-29 UTC. **추가 viewer 검증 진행 중. 상용 출시 완료 판정이 아니다.**

## 실제 확인한 원인

- PDF의 기본 설정이 단일 페이지(false)였다. 세로로 스크롤해 다음 페이지를 볼 수 없고, 페이지 이동은 더보기 안에 있었다.
- PDF 연속 보기에는 슬라이더만 있고 두 손가락/더블 탭 제스처가 없었다. 확대·페이지 맞춤 컨트롤러는 단일 캔버스에서만 연결됐다.
- 연속 PDF 로딩 자리표시자가 고정 A4 비율이어서 크기·회전이 다른 페이지의 실제 비트맵이 나타날 때 높이가 바뀔 수 있었다.
- 단일 PDF 읽기 캔버스가 첫 DOWN을 받지 않아 후속 두 손가락 이벤트를 놓칠 수 있는 경로가 있었다.
- 한글 Rhwp는 wasm.pageCount 전체를 수집하고 가시 영역을 가상 렌더링한다. 첫 페이지만 파싱한다는 근거는 확인하지 못했다. **20페이지를 읽은 사실과 사용자의 특정 파일 문제가 재현됐다는 주장은 구분한다.**
- 한글에는 숨겨진 엔진 상태바 대신 사용할 쪽 번호·직접 이동이 없었다. 전역 다열/가로 보기 설정이 모바일 문서에 영향을 줄 수 있어 모바일 열기는 세로 단일 열로 고정했다. 이는 저장 문서 조판 변경이 아니다.
- 새 다중 페이지 검사 중 끝 페이지를 스크롤 상단으로만 판정하면 앞 쪽 번호가 남는 것, 가로 화면으로 바꿀 때 픽셀 위치만 복원하면 읽던 쪽이 바뀌는 것을 재현했다. 화면 중심 쪽과 문서 내부 좌표 앵커로 수정했다.
- Word/Excel/PowerPoint는 실제 Collabora 네이티브 엔진을 사용한다. getNumberOfPages 같은 존재하지 않는 API를 가정하지 않고, 번들 SHA-256 검증 후 실제 goToPage, pageRectangleList, setPart, getNumberOfParts, _fitWidthZoom을 조사했다.

## 변경 내용

PDF는 다중 페이지의 기본값을 세로 연속 보기로 바꾸고 명시적인 단일 페이지 선택도 유지한다. 이전에 자동으로 기록된 false를 사용자 선택으로 오해하지 않도록 새 보기 설정 키를 사용한다. 페이지 수·크기·회전은 원본에서 읽으며 전 페이지를 논리 목록에 유지하고 보이는 주변 페이지만 비트맵을 소유한다. 고정 페이지 간격, 페이지 이동, 첫·마지막 이동, 50–400% 연속 보기 확대, 핀치 중심 보존·가로 이동·더블 탭·페이지 맞춤을 연결했다. 단일 편집 캔버스의 기존 내용 편집·저장 경로를 유지한다.

연속 PDF는 문서 변경 버전마다 native PdfRenderer 하나를 재사용한다. 미저장 PDF 본문/양식 변경은 한 번만 작업 사본으로 직렬화해 해당 버전 전체 페이지에 반영한다. 원본만 읽으면 별도 문서 파일을 쓰지 않는다. 페이지마다 최대2M픽셀, 비트맵 폐기와 renderer 종료를 분리하고 UI 스레드 밖에서 정리한다. 실제 시간 개선 여부는 동일 에뮬레이터 측정 후 기록한다.

한글은 실제 전체 페이지 가상 렌더링을 유지하고 쪽 번호·직접/이전/다음/첫/마지막 이동, 페이지 맞춤·다시 표시, 두 손가락·읽기 더블 탭을 연결했다. 보기/편집 전환은 같은 문서 인스턴스를 사용한다. 회전과 다른 화면 너비 복원에는 페이지·문서 좌표를 저장하며, 기존 zoom/scrollTop/scrollLeft 자료도 읽을 수 있다.

Office는 읽기 상태의 작은 페이지/슬라이드/시트 탐색 줄을 추가했다. 페이지·슬라이드는 실제 엔진 이동, 시트는 읽기 전용 시트 목록을 제공한다. 확대는 화면 배율이며 파일 서식 명령을 보내지 않는다. Excel에는 본문 페이지 번호를 강제하지 않는다. 편집/전체 화면에서는 탐색 줄을 숨긴다. Markdown/TXT의 원본 텍스트·인코딩·기존 읽기 위치/화면 크기 설정과 편집/변환 엔진은 유지한다.
