## 2. 실제 수정 사항

### 저장·복구

외부 파일을 변경하기 전에 앱 내부 provider-recovery에 원본, 최신 출력, SHA-256, 대상 URI, 저장 단계를 기록한다. 앱 프로세스 내 동기화와 프로세스 간 파일 잠금으로 저장 준비·쓰기·검증을 직렬화한다. 종료된 저장의 백업은 다음 시도로 대체하지 않는다. 외부 파일이 최신 결과와 일치하면 다시 쓰지 않고 확인할 수 있다. 앱 체크포인트 완료 뒤에만 해당 저널을 완료 처리한다.

저장 중단·실패 자료는 홈/설정의 **저장 복구**에서 이전 원본과 최신 편집본을 각각 새 파일로 꺼낼 수 있다. 복구 내보내기로 원본을 자동 덮어쓰지 않는다. 복구 삭제는 확인 후 선택한 내부 기록만 지우며 외부 문서는 삭제하지 않는다. 해시가 맞지 않거나 해석하지 못하는 기록은 자동 삭제하지 않는다.

SAF 제공자의 readback은 현재 읽히는 바이트 확인이다. 모든 제공자의 원자적 파일 교체, 외부 앱과의 compare-and-swap, 원격 클라우드 영구 반영까지 증명하지 않는다. 성공한 쓰기의 readback이 예상과 다르면 외부 변경일 가능성이 있어 무조건 롤백하지 않는다. 원본과 사본을 보존해 비교해야 한다. 전원 차단·모든 클라우드 제공자·저장 공간 고갈 전 범위를 검증한 결과가 아니다.

Office 모듈의 PDF·일반 내보내기·다른 이름 저장도 같은 저장 경로를 사용한다. 앱 모듈을 역참조하지 않고 기존 Application의 StudioDocumentHost 구현을 호출한다. 원본 URI 별칭, 허용 작업 경로, 실패 후 원본 소유권 변경, 저장 중 취소·닫기 충돌을 보호한다. 로딩 시작 표시 대신 실제 네이티브 완료 신호가 있어야 JNI PDF 필터를 호출한다.

### 서명

실제 PNG의 헤더·끝·디코딩·치수, 목록 수, 고유 ID, 획 수·좌표·압력·굵기를 제한한다. 손상 보관함을 빈 목록으로 바꾸지 않고 기존 자료와 이전 정상본을 보존한다. 확인 후 이전 보관함 복원과 개인정보를 포함하는 서명 복구 ZIP 내보내기를 제공한다. 보관 실패 시 표시 목록도 유지한다.

기존 자필 PNG 삽입·이동·크기 조절·표 셀 내 삽입·HWP/HWPX 저장·PDF 연동을 유지한다. 인증서 기반 전자서명이 아니며 문서 위 편집 가능한 벡터 필기 전체가 새로 구현된 것은 아니다.

### UI·오류·개인정보

- 기존 보기/편집 구분, 한 줄 상단과 형식별 하단 도구를 유지한다.
- 시스템 어두운 색상은 도구와 TXT/Markdown 읽기에 반영한다. 문서 원본의 용지·글자색은 바꾸지 않는다.
- 홈은 화면 폭·글자 배율에 따라 카드 수를 조정한다. 최근 문서 정렬, 이름 검색, 즐겨찾기, 숨김 목록과 복원을 제공한다. 목록 숨김으로 파일·복구본을 지우지 않는다.
- 첫 안내는 닫으면 다시 표시하지 않는다.
- 변환 결과가 미저장이면 교체·종료를 확인한다. 실제 기록·검증 중에는 중복 요청·취소를 제한한다.
- 이번에 수정한 앱 공통 작업과 저장·변환 경로는 오류 원문·문서명·경로를 보여주지 않는다. 로컬 진단에는 오류 분류·시각·앱/API 버전·엔진 구분만 기록한다. 외부 오류 수집 서비스를 새로 도입하지 않았다. 엔진의 모든 오류/회전·파일 선택 흐름을 전수 검토한 것은 아니다.

앱은 문서·서명·변환 결과를 서버로 전송하는 기능과 INTERNET 권한을 사용하지 않는다. OCR은 번들 Google ML Kit다. 이 권한 검사만으로 Google Play 서비스 IPC·SDK·운영체제 전체에서 통계 처리가 전혀 없다고 단정하지 않는다. 계약·정책 검토와 네트워크/IPC 실측이 추가로 필요하다.

사용자가 선택한 클라우드 파일 제공자나 공유 앱은 자신의 권한으로 외부 전송할 수 있다. 앱의 INTERNET 권한 부재를 외부 서비스까지 오프라인이라는 뜻으로 안내하지 않는다.

앱 내부 자료는 OS 앱 저장소에 보관하며 전체를 별도 암호화하지 않는다. 선택한 .dsbackup 내보내기만 기존 AES-256-GCM을 사용한다. 앱 삭제·데이터 삭제는 복구본과 내 서명을 지운다. 외부에 저장·공유한 파일은 별도로 관리해야 한다.

### 실패 분석과 실제 파일 검증

최초 전체 검사의 두 실패는 PPTX 메뉴 탐색과 새 native PDF 실패 복구 시나리오였다. 뒤의 실패는 finally의 종료 대기가 최초 예외까지 가렸다. 실제 로그에서 PDF 스레드의 `LOActivity_saveAs+124` SIGABRT를 확인했고, `documentLoaded`가 WebView URL 요청 직후 true가 되는 것을 찾았다. 실제 엔진의 완료 신호를 검사하도록 수정했다. 시험용 ready도 동일한 기준을 사용하며 최초 실패·단계별 화면과 상태를 보존한다. 종료된 프로세스를 제공자 조회로 다시 만드는 검사도 피한다. PPTX 메뉴의 실제 표시·터치 검사와 PDF 내부 내용 검사를 삭제하지 않았다.

집중 검사는 10장PPTX의 순서·비율·내용과 편집 후11장PDF, DOCX2쪽·머리말/꼬리말, XLSX2시트·수식 결과, Android 터치 주입 HWPX 자필서명→저장→엔진 재열기→서명 포함PDF, TXT/MD/PDF 변환을 포함한다. 실패 주입은 기존 PDF 쓰기와 롤백을 둘 다 실패시켜 이전 PDF와 최신2쪽PDF 보존, 불확실한 같은 대상 재시도 차단, 새 파일 저장·재열기, 원본 해시 유지를 확인한다.

### 보안·라이선스의 실제 범위

공개 Maven 권고 조회에서 Log4j API2.24.3의 [GHSA-qv9r-c865-cp47 / CVE-2026-49844](https://github.com/advisories/GHSA-qv9r-c865-cp47)가 일치했다. 동일 JSON 숫자 검사에서 이전2.24.3은1건 실패, 수정2.25.5는1건 통과했다. 실제 Maven JAR의 NOTICE도 별도 앱 자산으로 보존하고 공개 체크섬·내용을 대조한다. 이 체크섬을 서명/신뢰 인증으로 표시하지 않는다. 검토하지 않은 활성 권고가 있으면 배포를 차단한다.

### 전체 회귀의 추가 실패와 판정 보완

### 자동 저장과 닫기 충돌의 실제 수정

8a1aeec2의 연속11건 Actions40806426578은10건 통과/1건 실패였다. Office의 상태 영역 분리·48px 터치와 PPTX 변환은 통과했고 HWPX 저장 후 닫기는 작업 복사본 저장 완료 뒤에도 편집 상태에 머물렀다. IME 대기만으로 해결됐다고 판정하지 않았다.

한글 호스트는 자동 저장 중 save 버튼을 비활성화하고, close도 pending이면 요청을 돌려보냈다. 입력 직후의 버튼 터치가 자동 저장과 겹치면 닫기 요청이 사라질 수 있었다. checkpointFlight를 공유해 진행 중인 결과를 기다리고, closeFlight로 중복 닫기를 합쳤다. 자동 복구 저장 중에는 저장 후 닫기 버튼이 요청을 받을 수 있게 했다. 저장 실패 시 닫지 않고, 입력/서식이 더 변경됐으면 최신 revision과 dirty 상태를 다시 저장·확인한다. 계속 새 입력이 있으면 닫기를 중단하고 편집을 유지한다.

실제 HWP/HWPX 엔진의 export를 지연시켜 이전8a1aeec2 호스트의 요청 유실을 재현하고 수정본에서 실패 보존·중복 닫기·새 서식 저장/재열기를 검사한다. 이 사전 재현은 의도된 실패이며 최종 검사 통과로 합산하지 않는다. 새 후보 533896f7f0eaf57d23a76b089d0c59f7a722a92a의 실제 결과로 갱신하기 전에는 배포하지 않는다.
